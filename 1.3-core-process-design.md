# Part 1.3: Core Process Design

E-commerce System MVP – Product Manager Assignment

**Processes chosen:**

1. **Customer order and payment process.** It is the revenue-critical path and covers all four required exception scenarios.
2. **Order cancellation process.** It shares the same order state machine and covers inventory release, refunds and race conditions, which are where transaction systems most often break.

**Design principles used in both:**

- **Order status and payment/refund status are separate fields.** This keeps the order state machine simple and lets payment problems be handled without corrupting order state.
- **Stock is reserved (locked) at order submission, not at "Add to Cart".** Reserving at cart stage lets abandoned carts block real sales.
- **Every status change is conditional.** A transition only succeeds if the order is in the expected "from" status, so concurrent actions cannot corrupt state.
- **The payment callback is the source of truth.** The front-end "payment success" page is never trusted on its own.

## Process 1: Customer Order and Payment

### 1.1 Normal Flow

| Step | Actor | Action | System Behavior |
|---|---|---|---|
| 1 | Customer | Adds items to cart, or taps "Buy Now" | Checks that the product is on shelf and has stock. Cart shows current price. |
| 2 | Customer | Goes to checkout | Re-validates every item (on shelf, stock, price). Shows order confirmation page with address, items, and total. |
| 3 | Customer | Selects address and taps "Submit Order" | In one transaction: re-checks stock, locks stock for each SKU, creates the order with a unique order number and a price snapshot, sets status Pending Payment, and sets the payment deadline (e.g., 30 minutes). |
| 4 | Customer | Is taken to the payment page and pays | System creates a payment record (status Processing) and calls the payment gateway. |
| 5 | Payment Gateway | Sends asynchronous callback | System verifies signature, order number and amount, then marks payment Success, order Paid, and converts the stock lock into an actual deduction. |
| 6 | System | Notifies customer and operations | Customer sees "Payment successful". The order appears in the operations "To Ship" list. |

### 1.2 Exception Scenarios

| Scenario | Trigger Point | Handling | Result |
|---|---|---|---|
| Insufficient inventory | At checkout or at "Submit Order" (another buyer took the last units) | The stock lock uses an atomic conditional update (deduct only if available ≥ requested), so overselling is impossible even with concurrent buyers. If any item fails, the whole order fails and nothing is locked. The message names the item and the available quantity: "Only 2 left. Adjust quantity or remove item." The customer returns to the cart with selections preserved. | No order is created. No stock is held. |
| Payment failure (declined, insufficient funds, gateway error, user cancels on payment page) | Step 4 | Payment record is marked Failed with the reason code. Order stays Pending Payment and stock stays locked until the deadline. Customer sees "Payment failed" with the reason and a "Retry" button, and can switch payment method. Each retry creates a new payment record under the same order. | Order unchanged. Customer can retry within the time window. |
| Payment timeout | Payment deadline reached | A scheduled job closes the order: status becomes Cancelled (reason: "Payment timeout"), locked stock is released, and the customer is notified. | Order cancelled. Stock returns to sellable inventory. |
| Late payment after timeout | Callback arrives for a Cancelled order | In MVP the safe rule is automatic full refund to the original payment method and a message to the customer. The case is logged for the admin abnormal-order queue. | Customer is never charged without an order. |
| Product taken off sale but still in cart | Customer opens the cart or goes to checkout | Cart re-validates on every load. Off-shelf items are shown greyed out with the label "No longer available", are excluded from the selection and total, and offer a "Remove" button. If the product is taken off the shelf after the customer opens checkout, the Submit Order check blocks the order with a clear message and returns the customer to the cart. | Off-shelf items can never be purchased. Other items can still be ordered. |
| Price changed since adding to cart | Cart load / Submit Order | Cart always shows the latest price. If the price changed before submission, the customer sees "Price updated" and must confirm. After submission, the order keeps its price snapshot, so later price edits never change existing orders. | No surprise charges. |
| Duplicate submission (double tap, network retry) | Submit Order / Pay | The client sends an idempotency token. The server returns the existing order rather than creating a duplicate. Payment callbacks are also processed idempotently. | One order, one charge. |
| Callback lost or delayed | After payment | A scheduled job actively queries the gateway for any order stuck in Pending Payment with a Processing payment record, and syncs the result. | Paid orders are never left as unpaid. |

### 1.3 Status Changes

**Order status**

| From | Trigger | To | Side Effects |
|---|---|---|---|
| (none) | Customer submits order, stock lock succeeds | Pending Payment | Stock locked, payment deadline set |
| Pending Payment | Payment success callback verified | Paid | Stock deduction confirmed, appears in ops "To Ship" list |
| Pending Payment | Customer cancels, or deadline reached | Cancelled | Stock lock released |
| Paid | Operations confirms shipment | Shipped | Tracking number saved |
| Shipped | Customer confirms receipt, or auto-confirm after N days | Completed | Order closed |

**Payment status:** Unpaid → Processing → Success, or Failed (retry creates a new record). Success → Refunding → Refunded when a refund occurs.

**Order state diagram (text form):**

```
Pending Payment --pay success--> Paid --ship--> Shipped --confirm--> Completed
       |                          |
       +-- timeout/cancel --> Cancelled <-- cancel before shipment --+
```

## Process 2: Order Cancellation

### 2.1 Scope

| Case | Customer Can Cancel? | Handling |
|---|---|---|
| A. Unpaid order | Yes, anytime before the deadline | Direct cancellation, no money involved |
| B. Paid, not yet shipped | Yes | Cancellation with automatic full refund |
| C. Already shipped | No | Cancel button is hidden. Customer is directed to the return/after-sales flow (P2, outside MVP). |

### 2.2 Normal Flow

**Case A: Unpaid order**

| Step | Action | System Behavior |
|---|---|---|
| 1 | Customer taps "Cancel Order" on a Pending Payment order and selects a reason | Shows confirmation dialog |
| 2 | Customer confirms | Conditional update: Pending Payment → Cancelled, only if still unpaid. Stock lock is released. |
| 3 | System | Notifies customer. Order stays in history as Cancelled. |

**Case B: Paid, not yet shipped**

| Step | Action | System Behavior |
|---|---|---|
| 1 | Customer taps "Cancel Order" on a Paid order and selects a reason | Shows what will happen: "Full refund to original payment method within X business days" |
| 2 | Customer confirms | Conditional update: Paid → Cancelled, only if the order has not been shipped. This check and the update happen atomically. |
| 3 | System | Creates a refund record (status Refunding) and calls the payment gateway for a full refund. Stock is returned to sellable inventory. |
| 4 | Gateway | Confirms refund. Refund status becomes Refunded and the customer is notified. |
| 5 | System | Removes the order from the operations "To Ship" list. |

**MVP decision:** Cancellation before shipment is auto-approved with no manual review. It is the cheapest option and gives the best customer experience. Manual approval can be added later if abuse appears.

### 2.3 Exception Scenarios

| Scenario | Handling |
|---|---|
| Customer cancels while operations is shipping (race condition) | Both actions are conditional status updates on the same order, so exactly one wins. If shipment is confirmed first, the cancel request is rejected with "This order has already shipped. Please use return/after-sales after receipt." If cancel wins first, the ship button shows "Order cancelled" and operations stops packing. |
| Customer cancels while payment is in progress | Cancellation is blocked until the payment result is known ("Payment is being processed, please try again shortly"). This prevents a paid-but-cancelled mismatch. |
| Refund call fails (gateway error, network) | The order stays Cancelled and the refund record is marked Failed. The system retries automatically (e.g., 3 times with backoff). If it still fails, the case enters the admin abnormal-order queue for manual refund. The customer sees "Refund in progress". |
| Insufficient stock found by operations after payment (counting error, damaged goods) | Operations can cancel the order with reason "Out of stock". The same flow runs: full automatic refund, stock correction, and a customer notification with an apology. |
| Duplicate cancel or refund requests | Cancel and refund actions are idempotent. A second request on an already Cancelled order returns the current result without creating a second refund. |
| Cancel request after auto-confirm or completion | Rejected. Completed orders cannot be cancelled. |

### 2.4 Status Changes

| From | Trigger | To | Side Effects |
|---|---|---|---|
| Pending Payment | Customer cancels, or payment timeout | Cancelled | Release stock lock. No refund needed. |
| Paid | Customer cancels before shipment (auto-approved), or operations cancels | Cancelled | Restore stock, create refund record |
| Shipped / Completed | Cancel attempted | No change | Rejected with guidance to the after-sales flow |

**Refund status (separate from order status):** None → Refunding → Refunded, or Refunding → Failed → (retry) → Refunded, or Failed → manual handling by admin → Refunded.

**Audit:** Every status change is written to an order log (timestamp, operator, reason). This supports customer service, reconciliation and dispute handling.

## Why This Design

- **Lock stock at submission, release on cancel or timeout.** This protects inventory from overselling without letting abandoned carts hurt sales.
- **Auto-refund for late payments and pre-shipment cancels.** The company should never hold money for an order it cannot fulfill. It keeps customer trust and avoids manual workload at MVP scale.
- **Separate order and refund statuses.** A refund can fail without making the order state ambiguous, and each side can be monitored independently.
- **Conditional status updates everywhere.** This removes the most common real-world bugs (double payment, cancel vs. ship conflicts) at the design level rather than patching them later.
